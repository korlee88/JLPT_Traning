# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project goal

A personal JLPT study tracker for the repo owner. Currently targeting **N4** (exam 2026-12-06). The plan is to keep extending this same project level by level — **N4 → N3 → N2 → N1** — over however long that takes. Treat every change as something that has to still make sense once a second and third level exist, not just as a one-off for N4.

## Commands

```bash
npm install       # once, for the test toolchain (playwright)
npm start         # serve locally: python3 -m http.server 8000
npm test          # test/smoke.js — headless-browser regression check
```

There is no build step and no linter configured — it's intentionally a plain static site (`index.html` / `style.css` / `app.js`, no framework, no bundler). Don't introduce one without a concrete reason.

Deploy is automatic: push to `main` → `.github/workflows/deploy-pages.yml` → GitHub Pages at `https://<owner>.github.io/JLPT_Traning/`. There is no CI beyond that workflow, so `npm test` is the only thing standing between a bad commit and production — run it before every push that touches `app.js`, `index.html`, `style.css`, or any `data/**/*.json`.

## Architecture

- **One active level at a time.** `CURRENT_LEVEL` in `app.js` picks which `data/<level>/` folder the app reads. `data/levels.json` is a registry of levels that exist, but the app doesn't read it yet — there's no level switcher UI. Don't build one until a second level actually has data; until then it's dead code.
- **All state is client-side.** `localStorage` only, keyed per level (`jlpt_daily_checklist_<level>`, `jlpt_quiz_results_<level>`), no backend, no accounts. This is a single-user personal tool — don't add a server or auth for it. Both are day-keyed (`{ "2026-09-13": {...} }`) the same way, so "resets at midnight" falls out for free from `todayStr()` returning a new key — no explicit reset logic exists or should be added.
- **Two views of the same schedule, kept in sync by hand.** `STUDY_PLAN.md` (human-readable) and `data/<level>/plan.json` (what the app renders) describe the same weekly breakdown. There is no generator linking them — if you change one, update the other, or they will silently drift. What a machine *can* check is checked: `test/smoke.js` asserts the weeks tile the period with no gap, that week 1 starts on `startDate` and the last ends on `examDate`, and that every week carries 7 non-empty day lines. The per-day text itself only lives in `plan.json`; `STUDY_PLAN.md` carries the weekday *pattern* rather than all 56 strings, because duplicating those by hand is drift waiting to happen.
- **Two tabs: 쪽지시험 and 한자 기초.** 오늘 체크 (week card, daily checklist, 14-day streak) and 전체 계획 (the week table) were removed on 2026-10-17 — four days of use and the owner called them "쓸대없는 모니터". Gone with them: `CHECKLIST_ITEMS`, `CHECKLIST_AUTO_MAP`, `autoCheckFromQuiz`, the `jlpt_daily_checklist_<level>` reader/writer, `renderStreak`, `renderPlanTable`, and `plan.json`'s `dailyBase` (its only renderer was the week card). `plan.json` itself stays: `renderTopbar()` still reads it for the D-day and the day's task. The old checklist data is left in localStorage rather than cleared — it costs nothing and nothing reads it. **Don't rebuild a progress screen without being asked**: the one that existed was looked at and found not worth the taps.
- **The top of the page says what to do today, not just this week.** `#today-task` sits in the topbar — above the tab row, so it is on screen from all four tabs — and shows `10/13 (화) · 문법 p.82~ 동사 그룹·활용 시작 + 한자 쪽지시험`, built by `dayTaskFor()` from the current week's `days`. **`days` is stored Monday-first** (every week in the plan starts on a Monday and that is how the table reads) while `Date#getDay()` counts from Sunday, so the lookup shifts by `(getDay() + 6) % 7` — an off-by-one here renders the wrong day's task every day without ever throwing, which is why a test checks it against the data on four dates. Outside the plan period the line shows `plan.preStart` before the start and nothing at all after the exam (`hidden`, so no empty box). Its CSS sets no `display`, the `.quiz-replay` trap again.
- **Dates come from the real clock, always.** `todayStr()` formats `Date` using local `getFullYear/getMonth/getDate`, never `toISOString()`. `toISOString()` converts to UTC, which shifts the calendar date during early-morning hours in KST and would make the app show the wrong week/D-day for part of the day. `test/smoke.js` mocks `Date` (see `withFixedDate`) to check week/D-day logic at plan boundaries (before start, week 1, exam day, after exam) — extend those cases if you touch that logic.
- **Assets are cache-busted at deploy time, and the page says which build it is.** Twice the owner reported a just-shipped feature "안 보여" while the deployed files were verifiably correct — their phone was holding an `app.js` from several deploys back. `index.html` therefore references `app.js?v=dev` / `style.css?v=dev` and carries `<footer class="buildstamp">build dev</footer>`; the deploy workflow runs one `sed` that rewrites every `dev` marker to the commit SHA before the artifact is uploaded. Each build then has its own asset URL, so a cached `index.html` is the only thing that can go stale, and only until it revalidates. **This is the single exception to "no build step"** — it runs in CI only, so `npm start` and `npm test` see the plain `dev` marker and are untouched. When a report of "it isn't showing" comes in, ask what the footer says first: if it isn't the current SHA, it's cache, not code. `test/smoke.js` asserts both hooks exist, so renaming them can't silently pin phones to an old build.
- **GitHub Pages deploy gotcha (already hit once):** the first deploy failed with `Branch "main" is not allowed to deploy to github-pages due to environment protection rules`. Fix is in the repo owner's GitHub Settings, not in code: Settings → Environments → `github-pages` → Deployment branches and tags → set to "No restriction". Claude's GitHub App token also cannot call the Actions API to trigger or re-run a workflow (`403 Resource not accessible by integration`) — recovering a failed Pages deploy needs a human to click "Re-run jobs" or push a new commit.
- **The quiz prompt is deliberately oversized — for single-word prompts.** `.quiz-prompt` is `2.6rem` — double its original `1.3rem` — because the owner studies off a phone and has to make out kanji strokes. Don't "tidy" it back down for 한자/단어/가나/외래어, where one word fills the line and stroke legibility is the whole point. Sentence-shaped prompts get their own size instead: `.quiz-prompt.passage` is `1rem` for 독해, and `.quiz-prompt.sentence` is `1.2rem` for 문법. **The 문법 one reverses the earlier "accepted trade"** that long sentences may wrap over several lines — the owner asked for "절반넘게" on 2026-10-07 and was right, because the premise had changed under it: 문법 sentences carry their own furigana as `漢字（かな）`, which roughly doubles the character count *and* puts the reading right beside the kanji, so stroke-level legibility is no longer doing any work there. At 2.6rem one sentence ran over three lines and pushed the choices off a phone screen; at 1.2rem it is two lines and the whole question fits. `renderQuestion` clears `sentence` alongside `passage` on every question, or 한자 would inherit the small size — `test/smoke.js` asserts 문법 is under half 한자's computed size and that 한자 is still over 40px.
- **Verify every merge, even a clean one.** Realigning the working branch with `main` after a squash-merge has twice produced *silently duplicated code with no conflict markers* — once a duplicated `speak()`/`pickDistractors()` in `app.js`, once a duplicated `const` in `test/smoke.js` that would have been an outright `SyntaxError`. After any merge, before pushing: run `node --check app.js && node --check test/smoke.js`, grep for duplicate declarations, and diff against the pre-merge commit (a realign-only merge should produce an **empty** diff). Then `npm test`.

## Adding a new level (N3, then N2, then N1)

1. Create `data/<level>/` with `plan.json`, `vocab.json`, `grammar.json` matching the schemas below.
2. Add an entry to `data/levels.json`.
3. Write the human-readable plan (a new `STUDY_PLAN_<LEVEL>.md`, or extend `STUDY_PLAN.md`) — whichever the repo owner prefers at the time; ask if it's not obvious from how N4's was used.
4. When that level becomes the one actively being studied, switch `CURRENT_LEVEL` in `app.js`. Old levels' checklist history stays intact under its own storage key.
5. `npm test` before pushing.

**Schemas** (see `data/n4/*.json` for real examples):

```
plan.json       { startDate, examDate, textbook, preStart,
                  weeks: [{ week, start, end, focus, days: [7 strings] }] }
                  `days` is indexed MONDAY-first; `preStart` is the top line
                  before startDate. `focus` is data only — the week card that
                  rendered it went with the 오늘 체크 tab
hiragana.json   [{ char, hangul }]                      quiz asks for the Korean reading
                                                          (46 base + 20 탁음 + 5 반탁음 = 71)
katakana.json   [{ char, hangul }]                      same shape as hiragana.json
loanword.json   [{ word, meaning }]                     katakana 외래어; quiz gives the Korean
                                                          meaning and asks for the spelling, so
                                                          `meaning` must be unique across the file
                                                          or two entries become indistinguishable
vocab.json      [{ word, reading, meaning }]           quiz asks for meaning
kanji.json      [{ word, reading, meaning }]            same shape, quiz asks for reading instead
grammar.json    [{ sentence, meaning, choices: [4 strings], answer, note }]
                  `sentence` carries furigana as 漢字（かな）and one ＿＿＿ blank;
                  `choices` are bare suffixes that attach where the blank sits
reading.json    [{ passage, ruby, translation, question, questionTranslation,
                     choices: [4 strings], answer, note }]
                  `ruby` is the same text with 漢字（かな）furigana; stripping the
                  annotations must reproduce `passage` exactly (a test checks it).
                  `translation` is the passage in Korean, shown after answering;
                  `questionTranslation` is the question in Korean, shown with it
listening.json  [{ script, meaning, choices: [3] }]     quiz speaks `script` via Web Speech API;
                                                          `choices` are 3 authored near-misses of `meaning`
gloss.json      { "<kanji run>": { "<reading>": "<Korean>" } }   the tap glossary for 독해·문법.
                                                          Keyed by run AND reading — 行（い）and
                                                          行（おこな）are different words
pattern.json    { chunks: { "<가나 덩어리>": "<Korean>" }, blocked: [..] }  the kana half of
                                                          the same glossary — ました, ています,
                                                          なければなりません. `blocked` lists the
                                                          places a chunk would land inside a word
exam.json       { context[], synonym[], usage[], order[], cloze[], longread[],
                  infosearch[], task[], utterance[], response[] }
                  the ten 기출 formats no quiz type expresses. ONE file, not ten —
                  the 모의고사 page is their only consumer and they are not quiz
                  types (no QUIZ_KEY_FIELD, no review schedule of their own)
radical.json    { "<부수>": { name, sense, base?, chars: [..] } }  hand-verified 부수 groups;
                                                          feeds the post-answer note and the tab
kanjichar.json  { "<char>": { meaning, note } }         one row per radical.json character:
                                                          the Korean 훈음, and what the character
                                                          is built from. Covers it exactly — a
                                                          test asserts no gaps and no extras
```

**Every quiz type shows an explanation after answering** (right or wrong), via `explanationFor()` in `app.js` — not just a red/green highlight. For `grammar`/`reading` this is the data's own `note` field. Write one for every new entry, and make it earn its place: quote the exact sentence/clause that decides the answer, say *why* that leads to the correct choice, and account for the wrong choices — a superseded detail (the pre-change time/floor in the 会議 passage), a statement the text contradicts, or simply "not mentioned in the passage at all". `reading.json`'s notes were rewritten to that bar in #9 because a bare sentence pointer was too thin to learn from; match them rather than regressing. **`grammar.json`'s original 15 were still one-line pattern glosses** (`~かもしれません = ~일지도 모른다`) until #39 rewrote them alongside the 74 new entries — a file at two standards is worse than one, so raise the old entries when you extend a file rather than leaving a seam. A grammar note has one extra job the others don't: besides meaning, say which wrong choices fail on **접속** rather than on sense (`ながら` needs the ます형, `あとで` needs the た형), because that is half of what the real 문법 section tests. The other types don't need authored notes; `explanationFor()` builds the recap straight from the entry's own fields (e.g. `word (reading) = meaning`).

`hiragana`/`katakana` carry **104 characters each — the complete chart**: the 46-character gojuon base, the 20 탁음 (が/ざ/だ/ば행) and 5 반탁음 (ぱ행) added 2026-10-05 when the owner asked for "그 땡땡 두개 넣으면 발음이 달라지는것", and the 33 요음 (きゃ/しゅ/ちょ…) added 2026-10-06. **`ぢゃ`행 is deliberately left out**: it is vanishingly rare in modern Japanese, standard kana charts omit it or bracket it, and adding it would only create another pair indistinguishable from `じゃ`. 탁음/반탁음/요음 have no 어두/어중 split in the 표기법, so each has one form. There is nothing left to add — this file is finished unless the 표기법 itself changes.

`hangul` uses the **어중·어말 (aspirated) form** from 국립국어원's 외래어 표기법: か→카, た→타, ち→치, て→테, と→토. `つ`→쓰 is unchanged because the 표기법 gives it 쓰 in both positions. **Don't "correct" these back to the 어두 forms (가/다/지/데/도)** — the owner raised this on 2026-09-17 and the switch was deliberate:

- A lone kana has no word position at all, so applying the 어두 rule to it was already an arbitrary choice, not the standard being followed.
- Japanese word-initial voiceless stops sit *between* Korean 예사소리 and 거센소리, which is why perception splits; the 1986 committee judged them closer to 예사소리, and that call is still disputed.
- Decisively: the 어두 form collides with dakuten. か=가 *and* が=가, た=다 *and* だ=다, ち=지 *and* ぢ=지 — so the quiz would become unanswerable the moment が행 is added. The aspirated form keeps each pair distinct (か=카 vs が=가).

**That last point stopped being hypothetical on 2026-10-05**, when 탁음/반탁음 went in. Every 청음/탁음/반탁음 pair now in the data reads differently (か카/が가, た타/だ다, ち치/ぢ지, つ쓰/づ즈, て테/で데, と토/ど도, は하/ば바/ぱ파), so every question stays answerable. `test/smoke.js` asserts that pair by pair against both files — reverting any of these to its 어두 form now breaks a test instead of silently breaking the quiz.

**Five pairs legitimately share a hangul value**, and must not be "fixed": お/を are both 오 (を really is /o/ in modern Japanese); じ/ぢ are both 지 and ず/づ both 즈 — the 四つ仮名, genuine homophones in standard modern Japanese, which is exactly why the 표기법 gives them one spelling each; and 요음 brought two more, ざ/じゃ (자) and ぞ/じょ (조), which the 표기법 really does transcribe identically. `test/smoke.js` pins the count at exactly 5, so a sixth cannot appear unnoticed. What this *did* require is the dedupe `pickDistractors` previously lacked: it filtered distractors against the answer's value but not against each other, so a round could render 지 twice. It now dedupes by value, the way `pickReadingDistractors` already did. A smoke test drives a whole kana round and asserts all four choices are distinct on every question.

ん is shown as 응, a teaching convention for the isolated mora — the official rule (always ㄴ batchim) only applies to ん attached to a word.

`vocab`/`listening` use the shared `pickDistractors()` helper in `app.js` to build the 3 wrong choices at random from other entries in the same file, rather than hand-authoring distractors — keep new entries reasonably distinct in meaning so auto-picked distractors stay plausible-but-wrong, not nonsensical.

**The 외래어 quiz asks in the spelling direction, and generates its own traps.** `loanword.json` is katakana loanwords; the quiz shows the Korean meaning and asks which katakana spelling is right, because that's the direction where 장음/촉음 actually matter — reading a katakana word back to Korean would never test them. `pickSpellingDistractors`/`katakanaVariants` build the wrong choices from the answer itself: a dropped or added `ー`, the look-alike pairs ソ/ン and シ/ツ, ツ vs small ッ, and a flipped 탁점 (`スーツ` → `スーヅ`/`スーシ`/`スーッ`). A `ー` is never appended past the final mora — nobody writes `バスー`, and a choice that broken is eliminated without being read. Six of the 52 entries are short enough to yield fewer than three variants; those top up from other entries' words.

**The kanji quiz picks its distractors by shape, not at random** (`pickReadingDistractors`). Random readings let the answer be found without reading the kanji at all: `売れる` against れんしゅう/げんき/いちど is settled by the trailing れる. The picker now prefers readings sharing the word's okurigana tail (`okuriganaTail`), then a similar mora count, then the same opening mora — measured over the current data, that cut "answerable from the okurigana tail alone" from 24% to 8% and "answerable from length alone" from 43% to 1%. It also dedupes by reading, because preferring similar readings would otherwise show a homophone pair as the same choice twice (none in `kanji.json` yet — `姉`/`お姉さん` collide on *meaning*, which the kanji quiz only shows as a hint). The remaining 8% is data-bound: `売れる` is still the lone `〜れる` reading in the file, so nothing can match its tail until another arrives.

**The 한자 and 단어 quizzes both let you peek at the reading.** Tapping the word (or the cue line under it) swaps `#quiz-reveal` from "글자를 누르면 읽는 법" to the actual reading — for when a kanji is simply unreadable and guessing blind would teach nothing. The reading *is* the answer here, so the peek is deliberately not free: `quiz.peeked` makes `selectAnswer` record the item as **not** recalled even when the chosen answer is right, so it stays in the wrong-answer queue below. Without that, peeking would clear exactly the words that still need drilling.

The 단어 quiz got the same line on 2026-10-01 — the owner wants to read the kanji rather than the furigana, and the reading used to ride along in the prompt as `用事 (ようじ)`, so the kanji never had to be read at all. It is **not** penalized there: that quiz asks for the meaning, so the reading is a hint, not the answer. The rule across the app is that a reveal costs you the review-queue credit only when what it reveals *is* that quiz's answer — which is why the 한자 quiz's 뜻 힌트 is free too. `wireReveal(el, cue, value, { penalize, alsoTap })` in `app.js` is the one place this is implemented; pass `penalize: true` only in that case. 19 of `vocab.json`'s entries are kana-only (`word === reading`), and the 단어 quiz skips the cue line for those rather than offering a reveal that repeats the prompt. `renderQuestion` resets both lines, their handlers and `quiz.peeked` on every question.

**The kanji quiz's meaning is a hint, not part of the prompt.** It used to sit in the hint line (`읽는 법을 고르세요 (뜻: …)`), which for a half-known word handed over the reading before the question was read; the owner asked for it behind a tap on 2026-09-24. `#quiz-meaning` now shows `💡 뜻 힌트` and swaps to the meaning on tap. Unlike the reading peek it deliberately does **not** set `quiz.peeked` — the meaning isn't the answer in a 한자 읽기 question, so using it is still recall. Its CSS sets no `display`, so `[hidden]` keeps working (the `.quiz-replay` trap).

**한자·단어 quizzes cross-link words that share a character.** The owner's observation on 2026-10-01 — knowing the base kanji helps infer a compound's meaning — measured out like this over the 273 words then in `kanji.json` + `vocab.json`: 257 distinct characters, only 68 of them in more than one word, and you would need the top 150 to cover 72% of the kanji entries. A separate 낱자 quiz is therefore close to as much memorisation as the words themselves and was **not** built. What was: 59% of 한자 questions and 39% of 단어 questions already share a character with another word in the data, so `relatedWordLines()` appends lines like `社: 会社(회사), 社会(사회)` to the post-answer note and lets the character's sense come out by triangulation.

- **Derived, never authored.** A character's own meaning is nowhere in the data, and writing one would be authoring a dictionary. The index (`buildXrefIndex`, `_xrefIndex`) is built once per page load from the files in `XREF_SOURCES`, so it gets denser on its own with every daily batch and there is nothing to keep in sync.
- **Crossing the two files is the point.** `kanji.json` alone reaches 54% of 한자 questions and 23% of 단어 ones; the union reaches 59% and 39%. A word in both files is indexed once.
- **Post-answer only.** During the question it would hand over the 한자 quiz's answer — `新聞社` shown beside `会社(회사)` gives away しゃ. `withRelated()` is called from `explanationFor`, nowhere else.
- **Each word carries its reading** — `社: 会社(かいしゃ, 회사)`. The owner asked for this on 2026-10-01 while reading the 한자 기초 tab: a bare `会社(회사)` teaches nothing if you can't read 会社 yet. `labelFor()` is the one formatter, used by both the note and the tab, and it drops the reading when `reading === word` so a kana-only vocab entry doesn't repeat itself.
- Capped at 3 characters × **1** word — it was 2 before the readings, which roughly doubled each entry's width. The longest note on current data is `自動車` at 5 lines, re-measured at 390×844 with the 다음 button still visible. The 한자 기초 tab has room and keeps showing every word. `test/smoke.js` asks the page what `relatedWordLines` produced and checks the note carries exactly that, including the no-shared-character case, the 1-word cap, and that a kanji-written word always shows its reading.

**The same note names the 부수 the character belongs to** (`radicalLines`, `data/<level>/radical.json`), added 2026-10-01 after the owner pointed out that the basic characters combine into new ones. They do: of the 211 characters then in `kanji.json`, 164 (78%) share a component with another. But a component plays one of two roles — the 부수 carries the meaning category, the 음부 carries the sound — and 1,306 of the 2,136 상용한자 (61%) are 形声字 built from both. The 부수 half is what helps infer a meaning, so that is what the line shows: `氵(삼수변, 물): 池 泳 海 港`.

- **`radical.json` is hand-verified, not derived — and that is the whole point.** The CHISE/IDS decomposition behind the cross-reference *cannot* give the 부수: it recurses into nested parts, so an automatic pass files `知` under `口` (really 矢), `社` under `土` (really 礻), `館` under `宀` (really 食), `集` under `木` (really 隹) and `起` under `土` (really 走). Shipping that would teach wrong facts in a study tool. The file therefore carries only groups checked one by one — **21 groups, 105 characters**, deliberately narrower than what an automatic pass would claim. Don't regenerate it from IDS.
- **A variant radical shows its standalone parent — `礻 (示)` — and Japanese text is marked `lang="ja"`.** The owner reported on 2026-10-01 that the `礻` head "생긴게 다른데": it did not match the same part inside `社` on the same card. The codepoint is right (`U+793B`), so the cause is rendering, and there are two candidates that could not be told apart from here — the page is `<html lang="ko">`, so the browser picks Korean glyph variants for Han characters, and `U+793B` is a rare codepoint that a phone may serve from a fallback font while a common character like `社` comes from the primary one. **Neither was reproducible in this container**, which has IPAGothic and WenQuanYi but no Noto CJK locale variants, so a `lang=ko` vs `lang=ja` render came out byte-identical. Both are blocked instead of diagnosed:
  - `base` in `radical.json` gives the five variant radicals their standalone parent (`氵水`, `亻人`, `扌手`, `刂刀`, `礻示`), rendered beside the glyph. Those parents are common characters present in every CJK font, so the head still says what the radical *is* even when the variant glyph renders oddly. `辶` and `艹` get none: `辵` and `艸` are rarer than the forms they would explain.
  - `lang="ja"` on every element that shows Japanese (`#quiz-prompt`, `#quiz-reveal`, `#quiz-meaning`, `#quiz-choices`, `#quiz-note`, and the tab's glyph/chips/word list). Correct for a Japanese study app independently of this bug — `直`, `画` and `骨` genuinely differ between the Korean and Japanese forms. Hangul in those elements is unaffected.
  - `test/smoke.js` asserts each head matches what `radical.json` implies and that all six places carry `lang="ja"`.
- Invariants the data must keep: every character is one that actually appears in `kanji.json`/`vocab.json`, no character is in two groups, no group has fewer than 2 members (a lone member has no siblings to show), and a 부수 that is itself a character in the data leads its own group (`言` heads 計試誘説語話議).
- **There is also a `한자 기초` tab**, added 2026-10-02 because the owner asked for a separate study page three times and kept being answered with the in-quiz line. The note only reaches you mid-quiz and on about half the questions; the tab is where you sit and look at the groups. Built on first open (`renderRadicalTab`, guarded by `_radicalTabRendered`) so its fetches don't delay the first screen. `test/smoke.js` checks the page against `radical.json` and `kanjichar.json` themselves rather than hardcoded counts, so growing either file can't leave the tab behind.
- **The tab was rebuilt on 2026-10-17** ("기초한자 업그레이드해서 외울수있도록 잘보이고 … 설명을 넣어줘 약간 시험처럼 해도 좋고"). It had been a row of chips per group: it fitted more on screen and taught nothing, because a chip is just the glyph again. **Items come back on a schedule, not a wrong/not-wrong flag.** `QUIZ_KEY_FIELD` in `app.js` names the field that uniquely identifies an entry per quiz type (`word` for vocab/kanji, `char` for hiragana/katakana, `sentence`/`passage`/`script` for grammar/reading/listening). `jlpt_review_<level>` holds `{ version: 1, migrated, types: { <type>: { <key>: { box, due } } } }` — not day-keyed, it accumulates. `recordAnswerOutcome()` moves an item one Leitner box up on a correct answer and straight back to box 0 on a wrong one, setting `due` to `REVIEW_INTERVALS[box]` days out; `buildQuizPool()` fills a round with whatever is due (most overdue first, lowest box as the tiebreak) — at most `REVIEW_SHARE` (half) of it — then with material never asked before. A new quiz type must get an entry in `QUIZ_KEY_FIELD` (using a field that's actually unique within that file) or its answers are silently never scheduled.

**The cap is still the whole point:** the first version took `size` review items, so once the queue held a round's worth, every round was 100% review and a word added today could not be drawn until every earlier mistake was cleared. The owner hit this on 2026-10-02 ("문항이 반복되는 빈도가 절반정도"). Either side spills past its share only when the other runs out, so a round is never short when the file can fill it.

**What the boxes fixed, and why the old design could not be tuned into it** (2026-10-16, "반복해서 봐도 잘 안 외워진다 방법없을까"). The queue was a wrong/not-wrong set: a wrong answer put a key in, **a single correct answer took it out forever.** In a 4-choice quiz a pure guess is right a quarter of the time, so an item you do not know leaves after four encounters on average — the app kept declaring victory on the learner's behalf, which is exactly what "I keep seeing it and it doesn't stick" feels like from the inside. Measured over the shipped functions, 60 simulated days of a learner guessing every answer: **29.4 kanji retired by luck**, 150 of 223 words ever asked. Re-run against the boxes: **0.00 wrongly reach 외움** (five consecutive correct recalls spread over 25 days is 1-in-1024 by chance, and one miss resets it), 182 of 223 ever asked, and 118 repeat sightings where the old design gave none. Both numbers come from driving the real `buildQuizPool`/box logic in a page, not a model of it.

- **`REVIEW_INTERVALS = [0, 1, 3, 7, 14, 30]`, `MASTERED_BOX = 5`.** Box 0 is same-day — a word you just missed is in the very next round. Reaching 외움 takes six correct recalls over 25 days, so a word met today can get there twice before the exam; that sizing is deliberate and should be re-checked if the horizon changes.
- **A first correct answer lands in box 1 (tomorrow), not box 0 and not retirement.** This is the whole change in one line: right once is not done.
- **An item scheduled but not yet due is deliberately skipped**, even when it would fit in the round. Pulling it early is what spacing exists to avoid, and the old design had no way to express "ask me about this one on Thursday". It is used only as a last resort, after due overflow, when the file cannot otherwise fill the round.
- **Equal priority is shuffled, and that is load-bearing.** `dueKeys` shuffles before it sorts, relying on `Array#sort` being stable: priority still decides across different `(due, box)` pairs, ties come out fresh every call. Without it the function returned `Object.keys` order — and right after the migration *every* item is `(box 0, due today)`, one tie covering the whole queue, so the round's two review slots served **the same two words every day, for ever**. The owner reported it the next day as "매일같은게 보임", and it was a defect in the boxes shipped the day before, not the content volume it sounds like. A test asserts both halves: many distinct leads over 40 calls on an all-equal schedule, and that a genuinely overdue item still leads every time.
- **The migration is guarded by `store.migrated`, not by "does a schedule exist yet".** An empty schedule gets written the first time any screen reads one, which on a phone easily happens before the legacy key is looked at — keying off existence meant a real queue could be skipped and silently lost. It was written that way first and the test caught it. `jlpt_wrong_items_<level>` is left in place rather than deleted: it costs nothing and is the only copy of that history. A legacy key never knocks an existing entry back to box 0.

**Question selection is uniformly random, and this has been measured.** Asked for on 2026-10-15 ("출제 랜덤 한번더 확인해줘"). `shuffle()` is a real Fisher–Yates (descending index, `j` drawn from `[0, i]`), not the `sort(() => Math.random() - 0.5)` that looks equivalent and is not. A Monte Carlo over the shipped functions in a real page — 20,000 rounds per type — found every entry drawn, counts flat (χ² 218 on 222 df for 한자, 69/89 독해, 72/88 문법; χ² at or under its df is as flat as it gets), no front-of-file bias, and the correct answer landing in each of the four choice slots equally often (χ² ≈ 2 on 3 df, for both the shape-matched 한자 picker and the kana one). **So when a round feels repetitive the shuffle is not the place to look** — it is the arithmetic two sections down, or the review cap doing its job: with a queue seeded past the cap, review takes exactly `floor(size × REVIEW_SHARE)` slots every single round, by design.

**The schedule has a face: the 복습 노트** (the 오답 노트 until 2026-10-16; the DOM ids keep the `wrong-` prefix, because renaming them would churn the CSS and tests for nothing). It had been steering rounds since #33 while being completely invisible — the only way to learn what you kept missing was to keep missing it. It sits on the 쪽지시험 start screen, under the type buttons, and is built by `renderWrongNote()` in `app.js`: one card per quiz type that has queued items, each with a count, an always-visible `오답만 풀기` button, and the item list behind a `<details>`. Added 2026-10-08 in the same breath as the shorter rounds, and for the same reason — drilling the six words you actually got wrong is the short path, where redoing eight full quizzes to meet them again is the long one.

- **Not a fifth tab.** The tab row already wraps 2×2 on a phone; a fifth button makes it 2+2+1. The note is quiz-adjacent anyway — the drill button belongs beside the quiz launchers.
- **The drill button stays outside the collapse.** Only the list folds. A 40-word 한자 queue would bury the quiz buttons above it, but putting the one action behind a tap-to-expand would undo the point of having it.
- **`reviewLine(type, item)` reuses the post-answer recap's own first line** (`explanationFor(...).split("\n")[0]`) for the five word-shaped types, so a list line and a note can't drift apart; the lines `explanationFor` puts *under* that first one (부수, 같은 글자를 쓰는 단어) belong in a note and not in a list. The three sentence-shaped types need their own label: a 문법 note is a paragraph (it shows the filled sentence — `answerSpeech` already builds it — plus the Korean), and what identifies a 독해 entry in a list is its question, not the translation that heads its recap.
- **Stale keys are pruned where they're noticed.** A scheduled key whose entry has since left the data file can never come up again, so it would sit there forever; `renderWrongNote` drops it, since that's the one place the file is already loaded. Harmless before the note existed (`buildQuizPool` just never matched it) and visible the moment a count is printed.
- **A card appears only for a type with something due *now*.** Eight cards reading "오늘 0개" would bury the one that has work in it. The running totals live in the one `#wrong-progress` line under the heading (`외우는 중 42개 · 외움 11개`), which shows even on a day with nothing due — "외움 11개" is the answer to "am I getting anywhere", and a day off from reviews is not a day of no progress. Each card repeats its own type's split in a `.wrong-sub` line.
- **A 오늘 복습 round is `startQuiz(type, { wrongOnly: true })`** — everything due for that type, shuffled, capped at the round length so it stays a short targeted session. It feeds the same `recordAnswerOutcome`, so a right answer pushes the word out to its next box rather than clearing it.
- **It fills today's badge but never overwrites it.** The `✓ 한자 (8/10)` badge means "today's 쪽지시험", and a drill is drawn entirely from items you already missed, so its score isn't comparable. If the type hasn't been taken today it records (you did study it); if it has, the fuller round's result stands. The checklist tick is unconditional — studying is studying.
- Repainted on every open of the 쪽지시험 tab and on return from a round, **not** at startup: `renderRadicalTab`'s guard doesn't fit here because the counts move, but its reasoning does — the fetches shouldn't delay the 오늘 체크 screen for a list nobody is looking at.

**Click a quiz choice by exact text, never by substring.** `test/smoke.js` was using Playwright's `{ hasText }` (a substring match) plus `.first()`, which silently clicks the wrong button whenever one choice contains another. `vocab.json` has both `정하다` (決める) and `다정하다/친절하다`, so a round that drew the pair answered the question *wrong* and the failure surfaced as "a peeked vocab reading still counts as recall" — a review-queue message for a selector bug. `clickChoice(page, text)` matches `textContent` exactly and asserts the choice is there; use it.

**Round length is per quiz type, and right now every type is the same.** `DEFAULT_ROUND_SIZE` in `app.js` is **5** and `QUIZ_ROUND_SIZE` — the per-type override — is **empty on purpose**, recording "nothing differs" rather than deleting a mechanism that was used twice in the week before it emptied. A round is still capped at the data file's entry count; that cap used to hold 독해 to 8, and stopped binding on 2026-10-05 when `reading.json` reached 41 entries, so every type now runs its full configured length. `test/smoke.js` asserts each type's expected round length, so changing one means updating `EXPECTED_ROUND_SIZE` there too — and reading the length off the page (`quiz.pool.length`) rather than hardcoding it, which a kana block was doing until the round shrank under it and the failure surfaced as a click on a disabled button.

**The unit of work is the day, not the round** (2026-10-08, "다하기 많네"). `hiragana`/`katakana`/`kanji` ran 20 because each question is single-item recall and goes fast — true per question, and beside the point: eight quizzes with three of them at 20 is over 100 questions before the daily 기출 어휘 batch. That round took them to 10 and 독해/청해 to 5, and **a week of living with it took the rest to 5 too** (2026-10-15, "쪽지시험 5문제씩만하자"). Don't read the second step as the first one having been wrong: 5 is what gets done daily beside the day's main block, which is the number that matters. Shortening a round *raises* the repetition number below (fewer fresh slots per round means more rounds before you have seen everything), so neither step cost anything on that axis; what they cost is the days-to-master figure, which is the trade the owner asked for twice.

**A quiz type with barely more entries than its round size repeats *everything*.** The owner reported on 2026-10-05 that 독해 asked the same questions every day, and the cause was arithmetic rather than the review queue: `reading.json` had 8 entries against a round of `min(10, 8) = 8`, so **every round was the entire file** — 100% repetition, and no amount of review-cap tuning could change that. 33 original passages went in (8 → 41).

The next day the same report came in for 청해, where the ratio was less obvious: 40 entries against a round of 10 looks fine until `REVIEW_SHARE` is counted in. Half the round is review, so **only ~5 slots per round are fresh**, and 40 entries run out in about 8 rounds. The number to watch is therefore `entries ÷ (round × (1 − REVIEW_SHARE))` — rounds until a learner has seen everything — not `entries ÷ round`. 50 entries went in (40 → 90), taking 청해 to ~18. Check this whenever a quiz type's file is small; **it is the one failure mode that feels like a bug in the review queue and is not.**

Running that number over every type at that point put 문법 at **~3 rounds** on 15 entries — worse than either of the two that had already been reported — so it was flagged in #38 and fixed in #39 (15 → 89, ~18 rounds). The owner then asked for the whole app to be brought up to par at once, which #40 did: 독해 41 → 90, 외래어 52 → 90, and both kana files to the complete chart. **Every type now sits at ~18 rounds or better**, with 886 entries across the eight files. Re-run the number when any file changes rather than guessing from the entry count alone.

At a round of 5 the review cap takes 2 and 3 slots are fresh, which puts the eight types at: 가나 ~35 each (104), 외래어 30 (90), 단어 32 (96), 한자 ~74 (223), 문법 ~30 (89), 독해 30 (90), 청해 30 (90) — every type past 30 rounds before it has shown you everything.

**The cap is floored, not rounded** (`Math.max(1, Math.floor(size * REVIEW_SHARE))`). At a round of 5 rounding would give review 3 of the 5 slots — past half, which is the one thing `REVIEW_SHARE` exists to bound, and the failure mode the owner already reported twice. Even round sizes come out the same either way, so it went unnoticed until 독해/청해 went to 5 and now applies to every type. A test that recomputes the cap has to use `floor` and the round length it actually read off the page: one copy still said `Math.round(10 * REVIEW_SHARE)` and would have expected 3 where the app gives 2.

**Kana is the one type where this number means something different.** `hiragana.json`/`katakana.json` are a *closed set* — there is no "more content", only the rest of the chart — so seeing every character repeatedly is the goal rather than a defect. Their ~35 at a round of 5 is a *side effect* of shortening the round, not a goal — the table is 104 characters either way, and seeing it in smaller sittings is the point. Don't "fix" it by inventing entries.

**Every quiz reads its answer aloud once you've picked one.** Asked for on 2026-10-08 from the 외래어 quiz — the whole question there is a spelling (파티 → パーティー), and getting it right still leaves you unable to say it — and extended to 단어 in the same breath. `answerSpeech(type, item)` in `app.js` decides what to say, `selectAnswer` says it once and leaves `#quiz-say` (`🔊 발음 듣기`) for a repeat, and `renderQuestion` clears both. `ANSWER_SPEECH_RATE` is the plain 1.0, not 청해's `SPEECH_RATE` 1.15: that rate exists to match exam audio, and this isn't a listening test. It fires post-answer only, so the reveal-penalty rule never comes into it.

- **What gets spoken is the Japanese the question was about, which is not always the answer.** 가나 speak `char`, 외래어 `word`, 한자 `reading` — there the reading *is* the answer. **단어 is where the two come apart**: that quiz asks for the Korean meaning, and reading 만나다 back in a Japanese voice would teach nothing, so it speaks `reading` — what the prompt 会う actually sounds like.
- **문법 speaks the whole sentence with the blank filled**, not the bare suffix: a suffix has nothing to attach to, and 접속 is half of what that section tests. Both halves need `stripRuby` — the sentence carries `漢字（かな）` and several answers carry their own (`召（め）し上（あ）がり`) — or every annotated word would be read twice, once as kanji and once as its reading.
- **청해 gets nothing** (`answerSpeech` returns `null`, so the button stays hidden). Its script is spoken already and both replay buttons go unlimited the moment you answer, so a third control saying the same sentence would only crowd the screen.
- The button hides itself when `speechSynthesis` is missing rather than sitting there as a dead control, and its CSS sets **no `display`** (the `.quiz-replay` trap). It's styled secondary — it lands one tap from 다음, and two identical accent buttons stacked on a phone is a mis-tap waiting to happen.
- **Building it found a real data bug.** One 문법 sentence had a half-width `)` in its furigana (`休（やす)み`), so `stripRuby` never matched it — visible in the rendered prompt all along, and it would have been read aloud as part of the sentence. `test/smoke.js` now fills all 89 sentences and asserts each one comes out as clean Japanese (exactly one `＿＿＿`, every kanji annotated, no paren or blank surviving the fill). That's the 문법 counterpart of the `stripRuby(ruby) === passage` check 독해 already had, and the same lesson: a second copy of the text needs a machine check or it drifts.

**Listening quiz depends on the browser's Web Speech API** (`speechSynthesis`, `lang: "ja-JP"`) — there are no audio files. This means quality depends on whatever Japanese TTS voice the visitor's browser/OS provides (works well on Chrome desktop; may be silent or absent elsewhere). It degrades gracefully either way: the transcript is always revealed in the note after answering, so the quiz stays usable without audio.

**청해 was too easy, and it was the distractors.** The owner said so on 2026-10-02. With `pickDistractors` drawing the 3 wrong choices from *other entries'* meanings, catching one content word settled the question and the rest of the sentence never had to be parsed. Four changes went in together (#34); the first is the one that matters.

- **Authored near-misses.** Every `listening.json` entry now carries its own `choices`: three readings of the *same* sentence differing by one detail — a time, a day, a direction, who is doing it, a negation, 전/후. That is how real JLPT 청해 options work, and it means the whole utterance has to land. `renderQuestion` uses `item.choices` when present and still falls back to `pickDistractors`, so an entry added without them isn't broken — but write them.
- **14 → 40 entries**, so a round of 10 repeats less and the review cap above has fresh material to draw on. **40 → 90 on 2026-10-06**, when the owner reported 청해 repeating daily too. The arithmetic is the one the 독해 note below spells out, with the review cap folded in: a round of 10 is at most half review, so only ~5 are fresh, and 40 entries were exhausted in about 8 rounds. 90 stretches that to ~18. The 50 new ones also widen *what* the near-miss turns on — the first 40 mostly swapped a noun or a time, so the new batch hangs the distractor on grammar instead: 수수 표현 direction (`手伝ってくれました` vs 도와주었다/도와달라고 했다), 허가 vs 금지 vs 불필요 (`〜てはいけません` / `〜なくてもいい`), `〜ておく` vs `〜てある`, 가능 vs 사역 vs 수동, 조건의 반대 가지, 전문 `〜そうです` vs 추측 `〜そうです` vs `〜はず`, and 자동사/타동사 pairs. Scripts also run longer (11–34 characters, from 12–23), with two-clause sentences.
- **One replay** (`MAX_REPLAYS`). Unlimited replays made it a transcription exercise you could grind at; the exam plays each clip once. The button stays visible and disabled, labelled `(0회)`, so the layout doesn't jump and the reason is on screen. `quiz.replays` resets in `renderQuestion` like `quiz.peeked`.
- **`SPEECH_RATE = 1.15`** on the utterance. The default 1.0 is slower than natural conversational speed, which is what the exam uses.

**Two speeds, and the cap lifts once you've answered** (2026-10-05, both asked for by the owner). `speak(text, rate)` takes a rate; `replaysLeft(speed)` / `renderReplayButtons()` / `playCurrentScript(speed)` in `app.js` are the three places this lives.

- **`🐢 천천히` at `SLOW_SPEECH_RATE = 0.7`**, with its **own** budget of `MAX_REPLAYS` rather than sharing the normal one. They test different things: a second pass at full speed is another go at the same attempt, while a slow pass is for a sentence you couldn't segment at speed. Slow enough to separate the moras, not so slow the pitch accent falls apart.
- **After answering, both are unlimited.** `quiz.answered` is set in `selectAnswer`, and the buttons drop their `(n회)` label. The cap exists to stop the *question* becoming a transcription exercise; once the answer and the transcript are both on screen there is nothing left to grind, and replaying while reading the script is the most useful moment in the whole question. Don't reinstate a post-answer limit.
- Both buttons live in `#quiz-replays`, a flex row. Its `display` sits behind `:not([hidden])` for the same reason `.quiz-replay` did — a bare `display` beats the browser's `[hidden]{display:none}` and the row would show on every quiz type (the original `.quiz-replay` bug). Verified at 390×844: the two buttons fit on one line and 다음 stays reachable.

Invariants `listening.json` must keep (checked when the file is edited, and partly by `test/smoke.js`, which asserts the rendered four are exactly one entry's `meaning` + `choices`): exactly 3 distractors per entry, the answer not among them, no duplicate distractors within an entry, no distractor equal to *another* entry's meaning (that would make two questions share a correct-looking option), and no duplicate `script`/`meaning` across entries — `script` is the wrong-answer queue's key.

## N4 모의고사 (the 모의고사 tab)

Added 2026-10-22 ("N4 시험페이지를 만들어서 이전 시험출제와 흡사하게 기출고사형식으로 추가해줘"). The 쪽지시험 side already drills the content; what it cannot teach is what 85 questions in a row under a clock feel like, and which of the 15 もんだい you are actually weak at. So the exam reproduces the **shape** rather than inventing a friendlier one.

- **The real structure, and the real numbers.** Three sittings in the official order and counts — 문자·어휘 28문항/25분, 문법·독해 29문항/55분, 청해 28문항/35분, 85 questions in 115 minutes. `EXAM_SPEC` in `app.js` holds it; `test/smoke.js` builds all three and asserts every もんだい fills to its published count and that the three come to 85. **25/55/35 is the current (2022~) timetable**, not the older 30/60/35 — don't "correct" it back.
- **Scored on the official scale, which is not the same split as the sittings.** 언어지식(문자·어휘·문법)·독해 is **one 120-point block sat as two papers**; 청해 is its own 60. Pass is 90 total **and** 19 per block, so a 150 with a 15 in 청해 fails. `EXAM_SCALE` models that rather than just totalling 85 questions, because the 과락 is the part a learner forgets. A paper never sat reports **미응시**, not a scored zero — a paper you did not take is not a paper you failed, and showing 0/60 for it would make every single-paper sitting look like a fail.
- **Nothing is marked until you submit.** This is the whole difference from 쪽지시험, where the answer lands after every question. A picked choice gets `.picked` (accent fill), never `.correct`/`.wrong`; the notes all appear together behind `문제 다시 보기`. A test clicks a choice and asserts no graded class and no note is on screen. **Don't add per-question feedback here** — the 쪽지시험 is where that belongs, and having both makes neither one what it is.
- **Five もんだい draw from the quiz files, nine from `exam.json`.** 漢字読み/表記 come from `kanji.json`, 文の文法1 from `grammar.json`, 内容理解(短文) from `reading.json` — so those vary every sitting and get denser with each daily batch. The rest are formats no quiz type expresses and are authored.
- **The exam feeds the same Leitner schedule.** A question drawn from a quiz file carries `reviewType`/`reviewKey`, and `submitExam` calls `recordAnswerOutcome` for it — a word you missed under a clock is exactly a word to see again tomorrow. The exam-only formats have no key and are skipped, which is why the key is **set on the question** rather than inferred from the type at submit time.
- **`exam.json` is one file holding ten shapes**, against the repo's usual one-file-per-shape. They are not quiz types: no `QUIZ_KEY_FIELD` entry, no review schedule, one consumer, one fetch that only happens when the tab opens. Ten more files would be ten more schema rows for a feature with a single reader.
- **Furigana is visible and nothing is tappable.** Every authored sentence carries `漢字（かな）` inline the way `grammar.json` does, and 독해 uses the `ruby` field rather than `passage`. The real paper gives no furigana, but the owner cannot yet read a 중문 passage unaided and an exam you cannot read measures nothing. The tap glossary is deliberately **off** here — tapping a word for its meaning mid-exam is the thing an exam exists to stop.
- **표기 distractors are generated, and they have to look like the answer.** `kanjiLookalikes` swaps one character for a sibling from the same `radical.json` group (`洗` → `洋`/`海`/`港`), then falls back to a word of the same **kanji/kana shape**, then to anything. The shape rule is load-bearing: the first version offered `飛行機` against `有名だ`, which is settled by the trailing kana without reading a single kanji — the same failure `pickReadingDistractors` was built to fix. Measured over all 278 words: **85% of distractors are a one-character swap or share a character**, 0 are shape-mismatched, and every word yields exactly 3. `お正月` is the one word with no same-shape partner in the file, and it returned **zero** distractors until the last-resort fill went in — a question with two choices, which is why the test asserts the count rather than the quality alone.
- **A paper never asks the same thing twice, and that needed a fix.** 問題1 prints `飛行機` and asks for its reading; 問題2 then asks you to spell `ひこうき` a few questions later with the answer already on the paper above. The two もんだい drew from `kanji.json` independently, which put a duplicate in **12% of 문자·어휘 papers** (measured over 1,000) — and since both carry the same `reviewKey`, whichever landed second silently overwrote the other outcome in the schedule. `buildExamSection` now threads a `used` set of review keys through the builders (`pickUnused`), and a test builds every section 40 times and asserts no repeated key and no repeated question. Any new builder that draws from a keyed file has to take `used` and honour it.
- **청해 withholds the script, and degrades rather than breaking.** The dialogue is spoken (`speechSynthesis`, one replay like `MAX_REPLAYS`) and its text appears only in the review. If the browser has no speech synthesis at all the script is shown instead — otherwise the whole section would be blank, which is worse than easy. 問題1/2 are split by an authored `kind` field (`task` = 課題理解 "what next", `point` = ポイント理解 "which detail"), so the headings say what the question actually is; a test asserts there are at least 8 and 7 of them.
- **One paper's worth of authored items, not three.** `exam.json` holds 12 문맥규정, 8 유의표현, 6 용법, 8 문장조립, 2 글의문법 passages, 2 중문, 2 정보검색, 15 청해 대화, 6 발화표현, 10 즉시응답 — enough to fill every もんだい with room to shuffle, but **sit the same paper twice and the authored sections repeat**. The five file-drawn もんだい do not. Growing the authored pools is the obvious next step if the owner starts re-sitting.
- **No Latin letters in a spoken line.** `Mサイズ`/`Lサイズ` is real Japanese and the real exam prints it, but a `ja-JP` utterance reads Latin unpredictably, so the one item that used it was rewritten (`大きいサイズ`). A test checks every spoken line.
- **Three tabs is the most that fits one phone row** (342px of track at 390px, ~114px each, widest label 한자 기초 needs ~74px). `test/smoke.js` asserts the row renders on **one line**, so a fourth tab fails the test rather than silently wrapping to 3+1.

## Content accuracy and copyright

- Vocab/grammar entries must be standard, verifiable JLPT-level content — don't invent a word/reading/meaning or a grammar pattern that isn't real.
- Never transcribe the textbook's own exercises, example sentences, or passages into `data/`. Write original example sentences for the same grammar point instead — reference the pattern/level, not the book's text.
- **What the line actually rests on is publishing, not the words.** The owner pushed back on this (2026-09-21) and was right: vocabulary, readings and meanings are facts about the language, nobody's property, and JLPT publishes no official word list — so transcribing them was never the issue, and `loanword.json`'s 52 words are as fine as any daily batch. Two things do matter. **Scope:** any single drill item is too short and too obvious to be anyone's property, but lifting a whole exercise set item by item reproduces the *compilation*, which is the book's work. **Use:** copying a textbook for your own study is ordinary private use; this app is a public repo on public Pages, so the same copy becomes distribution. Treat a scan as a source of words, not as a set of questions to mirror, and the rest follows.
- Generating the 외래어 distractors was the better design regardless — the book's decoys vary item to item, while `katakanaVariants` hits 장음/촉음/탁점 systematically every round. Don't present it as merely a legal workaround.
- A **word/reading/meaning list** is on the right side of that line and may be transcribed (this is what the daily 기출 어휘 batches above do): `青い / あおい / 파랗다` is dictionary-level fact, not authored expression. What stays off-limits is the book's own sentences — its exercise items, example sentences, and reading passages.
